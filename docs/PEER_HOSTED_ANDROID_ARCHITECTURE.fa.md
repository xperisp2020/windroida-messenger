# معماری میزبانی شخصی چندسکویی و اتصال همتا‌به‌همتا در Windroida

## هدف محصول

هر نصب Windroida روی **Android یا Windows** بتواند بدون اتکا به یک سرور مرکزیِ نگه‌دارندهٔ حساب‌ها و پیام‌ها، یک میزبان مستقل ایجاد کند. دستگاه میزبان یک دعوت‌نامهٔ قابل اشتراک (لینک و QR) می‌سازد و کاربران دیگر از Android یا Windows با همان دعوت‌نامه به آن متصل می‌شوند. نقش میزبان و عضو به سیستم‌عامل وابسته نیست: Android می‌تواند به Windows وصل شود، Windows به Android وصل شود و دو دستگاه هم‌سیستم‌عامل نیز به هم متصل شوند.

هر میزبان یک فضای مستقل است؛ مفهوم «سرور اصلی جهانی» وجود ندارد. یک گوشی می‌تواند هم‌زمان میزبان فضای خودش و عضو فضای میزبان دیگری باشد.

## ماتریس سازگاری پلتفرم‌ها

| سیستم‌عامل دستگاه | میزبانی | اتصال به میزبان | وضعیت فعلی مخزن |
|---|---|---|---|
| Windows | بله، از طریق Python server فعلی و اجرای `start.bat` | بله، Web UI و کلاینت‌های سازگار | runtime سرور موجود است؛ ظرفیت قابل تنظیم در حال اضافه‌شدن است |
| Android | هدف نهایی؛ سرویس بومی foreground و runtime سازگار با پروتکل | بله، اپ Android فعلی کلاینت WebView است | فعلاً کلاینت است؛ میزبانی بومی هنوز پیاده‌سازی نشده |
| Windows ↔ Android | هر کدام می‌تواند میزبان شود و دیگری عضو | با endpoint مشترک و پروتکل یکسان | سازگاری پروتکل باید در آزمون‌های بین‌پلتفرمی اثبات شود |

**قاعده محصول:** انتخاب سیستم‌عامل نباید کاربر را به نوع خاصی از میزبان محدود کند. نام میزبان، شناسه، دعوت‌نامه، مجوزها، مدل چندکاربره و API باید مستقل از سیستم‌عامل باشند.

## وضعیت فعلی و فاصله تا هدف

- میزبان Windows در مخزن فعلی وجود دارد: `server.py` همراه با `start.bat` و سرویس‌های Python؛ این مسیر مبنای اولین میزبان قابل استفاده روی Windows است.
- اپ Android فعلی عمدتاً کلاینت WebView است و آدرس سرور را دریافت می‌کند؛ اجرای APK فعلی به‌تنهایی سرور کامل روی گوشی ایجاد نمی‌کند.
- سرور اصلی پیام‌رسان، Gateway، Ghab و Cloud Drive در حال حاضر سرویس‌های Python جداگانه‌اند.
- برای میزبانی Android باید runtime بومی/قابل‌حمل با همان قرارداد wire و API ساخته شود؛ صرفاً بازکردن پورت یا اجرای یک listener آزمایشی به معنی میزبانی کامل نیست.
- یک قرارداد پروتکل مشترک و نسخه‌بندی‌شده لازم است تا Windows و Android بتوانند با یکدیگر میزبان/عضو شوند و داده‌هایشان ناسازگار نشود.

## مدل نقش‌ها

1. **Host**: گوشی‌ای که سرویس Windroida را اجرا می‌کند و مالک پایگاه داده و فایل‌های همان فضای مستقل است.
2. **Member**: کاربری که با دعوت‌نامه به یک Host وصل می‌شود.
3. **Rendezvous (اختیاری)**: سرویس سبک برای معرفی مسیر اتصال دو طرف؛ حساب، پیام، فایل یا کلید خصوصی را نگه نمی‌دارد.
4. **Encrypted relay (اختیاری)**: فقط بسته‌های رمز‌شده را در صورت ناممکن بودن اتصال مستقیم عبور می‌دهد؛ نباید کلید رمزگشایی داشته باشد.

یک کاربر می‌تواند برای هر فضای مستقل یک عضویت جداگانه داشته باشد و نقش Host/Member به همان فضا محدود است. **هر میزبان باید بتواند چندین عضو را هم‌زمان بپذیرد**؛ همه اعضا از یک نشانی اتصال میزبان استفاده می‌کنند، اما هر نفر حساب، اعتبارنامه، کلید و نشست اختصاصی خودش را دارد. اشتراک‌گذاری یک رمز عبور مشترک بین اعضا مجاز نیست.

## تجربه کاربری

### ایجاد سرور روی گوشی

1. کاربر در صفحه «سرور من» گزینه «فعال‌سازی میزبانی» را انتخاب می‌کند.
2. برنامه پیش از شروع، فضای ذخیره‌سازی، مصرف باتری، محدودیت شبکه و عمومی‌بودن آدرس را توضیح می‌دهد.
3. کاربر یک نام برای فضای خود و سیاست عضویت را انتخاب می‌کند: فقط با دعوت، تأیید دستی یا عضویت آزاد (پیش‌فرض: فقط با دعوت).
4. برنامه کلید هویت میزبان را در Android Keystore می‌سازد؛ کلید خصوصی قابل خروجی‌گرفتن نیست.
5. سرویس میزبان با اعلان دائمی Android Foreground Service اجرا می‌شود.
6. برنامه وضعیت میزبان، نشانی‌های قابل دسترس، تعداد اعضا، مصرف ذخیره‌سازی و دکمه توقف را نمایش می‌دهد.
7. کاربر لینک و QR دعوت را برای یک نفر یا چند نفر می‌سازد و به اشتراک می‌گذارد. نشانی میزبان می‌تواند بین همه اعضا یکسان باشد، اما برای هر عضو باید توکن دعوت و حساب مستقل صادر شود.
8. در صفحه مدیریت میزبان، مالک سقف تعداد اعضای ثبت‌شده و سقف اتصال‌های هم‌زمان را جداگانه تعیین می‌کند؛ برنامه ظرفیت پیشنهادی را بر اساس RAM، فضای آزاد، وضعیت باتری و توان شبکه نمایش می‌دهد.

### اتصال عضو جدید

1. نفر دوم لینک را باز یا QR را اسکن می‌کند.
2. برنامه پیش از ارسال اطلاعات ورود، اثر انگشت کلید هویت میزبان و نام میزبان را نشان می‌دهد.
3. عضو اثر انگشت را تأیید می‌کند؛ در اتصال‌های بعدی تغییر ناگهانی کلید هشدار جدی است و اتصال به‌صورت پیش‌فرض متوقف می‌شود.
4. دعوت‌نامه با توکن تصادفی قوی، تاریخ انقضا، محدودیت تعداد مصرف و سطح دسترسی اعتبارسنجی می‌شود.
5. میزبان در صورت نیاز درخواست عضویت را تأیید می‌کند.
6. حساب عضو و کلیدهای رمزنگاری فضای مربوطه ساخته می‌شوند. هیچ دسترسی مدیریتی یا دسترسی به فایل‌های خصوصی گوشی میزبان به عضو داده نمی‌شود.

## قالب دعوت‌نامه

قالب مفهومی لینک:

`windroida://join?v=1&host=<host-id>&endpoint=<endpoint>&fp=<identity-fingerprint>&invite=<one-time-token>`

- `host-id`: شناسه تصادفی و پایدار فضای میزبان، نه شماره تلفن یا شناسه سخت‌افزاری.
- `endpoint`: نشانی اتصال فعلی؛ ممکن است چند مسیر داشته باشد.
- `fp`: اثر انگشت کلید عمومی هویت میزبان.
- `invite`: راز تصادفی حداقل 256 بیتی، محدود به یک میزبان، زمان انقضا و تعداد مصرف. هر دعوت تک‌مصرف است؛ برای چند نفر می‌توان دعوت‌های جداگانه ساخت یا یک بسته دعوت با تعداد مصرف محدود تولید کرد. در حالت بسته‌ای نیز هر بار مصرف باید یک حساب و اعتبارنامه مستقل بسازد.
- توکن دعوت فقط یک‌بار مصرف می‌شود؛ در پایگاه داده فقط hash آن ذخیره می‌شود.
- لینک دعوت نباید رمز عبور، کلید خصوصی، توکن نشست یا اطلاعات حساس کاربر را حمل کند.
- امکان لغو دعوت و چرخش کلید/توکن وجود دارد.

## معماری سرویس در Android و Windows

### Windows Host

- در نسخه فعلی، `server.py` موتور میزبان Windows است و `start.bat` وابستگی‌ها و اجرا را مدیریت می‌کند.
- سرویس باید به‌صورت process/service قابل توقف، شروع مجدد و پایش باشد؛ داده‌ها و گواهی میزبان در پوشه داده همان میزبان باقی می‌مانند.
- تنظیمات ظرفیت، اعضا، نشست‌ها و دعوت‌ها باید سمت سرور ذخیره و enforce شوند، نه فقط در رابط کاربری.
- کلاینت Windows و Android باید از همان endpoint و قرارداد پروتکل استفاده کنند.

### Android Host

- `HostForegroundService`: راه‌اندازی، توقف، اعلان دائمی، بازیابی پس از قطع شبکه و گزارش سلامت.
- `HostRuntime`: اجرای API و WebSocket روی loopback و رابط شبکهٔ مجاز؛ هیچ listener مدیریتی روی همه رابط‌ها بدون احراز هویت باز نشود.
- `HostDatabase`: پایگاه دادهٔ محلی با migration، تراکنش، پشتیبان‌گیری و بازیابی کنترل‌شده.
- `HostIdentity`: کلید هویت و امضای چالش‌ها با Android Keystore.
- `InviteManager`: ساخت، اعتبارسنجی، انقضا، لغو و مصرف اتمیک دعوت‌ها.
- `PeerConnectionManager`: تشخیص شبکه، مسیر LAN، IPv6/port mapping در صورت امکان، اتصال مستقیم و مسیر relay.
- `HostPolicy`: سقف اعضا، سقف اتصال هم‌زمان، سقف حجم هر عضو و کل میزبان، محدودیت درخواست، مسدودسازی، لغو نشست و مدیریت دسترسی.
- `CapacityManager`: محاسبه ظرفیت امن پیشنهادی با توجه به RAM، فضای ذخیره‌سازی، CPU، باتری، دما و پهنای باند؛ اعمال محدودیت سخت سمت سرور و جلوگیری از پذیرش عضو بیش از سقف.
- `MemberManager`: ایجاد حساب مجزا، نقش‌ها، وضعیت تأیید، تعلیق/حذف عضو و نمایش نشست‌های فعال.
- `HostStatus`: نمایش uptime، وضعیت اتصال، فضای آزاد و علت توقف.

سرویس باید در برابر Doze، خاموش‌شدن فرایند، تغییر Wi-Fi/شبکه، محدودیت سازنده گوشی و توقف اجباری قابل بازیابی باشد؛ اما اندروید تضمین نمی‌کند برنامه پس از Force Stop یا خاموش‌شدن دستگاه در دسترس بماند. توقف سرویس باید همه listenerها و نشست‌های شبکه را ببندد.

## چندکاربره بودن و تنظیم ظرفیت میزبان

### پیاده‌سازی فعلی در میزبان Windows

- جدول پایدار `host_settings` سقف اعضا و کاربران آنلاین را جداگانه نگه می‌دارد؛ مقدار صفر برای حفظ سازگاری نصب‌های قبلی به معنی بدون محدودیت است.
- عملیات پروتکل `host_limits` فقط به مالک اجازه تغییر سقف‌ها را می‌دهد و وضعیت ظرفیت را برمی‌گرداند.
- ثبت‌نام با تراکنش SQLite از نوع `BEGIN IMMEDIATE` سقف اعضا را اتمیک بررسی می‌کند؛ سقف اتصال هم‌زمان نیز زیر قفل مشترک نشست‌ها بررسی می‌شود.
- نشست چند دستگاهی یک حساب، یک کاربر آنلاین محسوب می‌شود؛ عضو جدید در صورت تکمیل ظرفیت رد می‌شود و نشست‌های قبلی قطع نمی‌شوند.
- پنل مالک در تنظیمات رابط مشترک Web، مقدار سقف‌ها و تعداد اعضا/کاربران آنلاین را نشان می‌دهد. این UI هم در مرورگر Windows و هم در WebView اپ Android استفاده می‌شود.
- این پیاده‌سازی فقط برای Windows Host فعلی قابل اجراست. Android در این مرحله کلاینت چندسکویی است؛ Android Host تا زمان ساخت runtime بومی و آزمون واقعی آماده نیست.

- یک آدرس میزبان می‌تواند نقطه ورود تعداد زیادی کاربر باشد؛ اتصال هر عضو به همان endpoint انجام می‌شود، اما احراز هویت، نشست، مجوزها و کلیدهای هر عضو مستقل است.
- مالک در تنظیمات «سرور من» دو مقدار مستقل تعیین می‌کند: **حداکثر تعداد اعضای ثبت‌شده** و **حداکثر کاربران متصل به‌صورت هم‌زمان**. برای مثال ممکن است سقف اعضا ۲۰ نفر و سقف اتصال هم‌زمان ۵ نفر باشد.
- گزینه‌های ساده می‌توانند شامل ۲، ۵، ۱۰، ۲۰ و مقدار سفارشی باشند. «بدون محدودیت» فقط در تنظیمات پیشرفته و همراه هشدار منابع ارائه شود؛ مقدار پیش‌فرض باید محافظه‌کارانه و متناسب با دستگاه باشد.
- اگر سقف اعضا پر شود، دعوت جدید پذیرفته نمی‌شود تا مالک ظرفیت را افزایش دهد یا عضوی را حذف کند. اگر سقف اتصال هم‌زمان پر باشد، کاربر جدید پیام روشن «ظرفیت اتصال تکمیل است» می‌گیرد؛ نباید نشست عضو دیگر بی‌اجازه قطع شود.
- محدودیت‌ها باید سمت سرور و به‌صورت اتمیک اعمال شوند؛ صرفاً مخفی‌کردن دکمه یا محدودیت رابط کاربری کافی نیست. درخواست‌های هم‌زمان نباید باعث عبور از سقف شوند.
- ظرفیت واقعی به مدل گوشی، RAM آزاد، فضای دیسک، سرعت شبکه، نوع ترافیک و مصرف باتری بستگی دارد. عدد ثابت برای همه گوشی‌ها قابل تضمین نیست. برنامه باید بار را پایش کند، هشدار بدهد و در صورت فشار شدید، پذیرش عضو جدید را موقتاً متوقف کند.
- مالک می‌تواند هر عضو را جداگانه تأیید، مسدود، حذف یا از همه نشست‌ها خارج کند و در صورت نیاز همه دعوت‌ها را یک‌جا لغو کند.
- عضوها به‌صورت پیش‌فرض هیچ دسترسی مدیریتی ندارند؛ نقش مدیر باید صریح، محدود و قابل لغو باشد.

## قرارداد مشترک و سازگاری بین پلتفرمی

- تعریف نسخه پروتکل، schema پیام‌ها، خطاها، کدهای ظرفیت پر، قالب دعوت و handshake مستقل از OS.
- برای Android و Windows، semantics ثبت‌نام، ورود، resume، اعضا، نشست‌ها و سیاست ظرفیت باید یکسان باشد.
- شناسه میزبان و اثر انگشت هویت نباید به مسیر فایل، نام دستگاه یا شناسه سخت‌افزاری وابسته باشد.
- تاریخ/زمان، encoding، اندازه payload و قواعد canonicalization باید در تست‌های مشترک ثابت باشند.
- تست‌های conformance باید روی Windows و Linux اجرا شوند و در مرحله Android روی runtime اندروید نیز اجرا شوند.
- سناریوهای اجباری: Android client → Windows host، Windows client → Windows host، Windows client → Android host و Android client → Android host.

## شبکه و آدرس‌دهی

### مسیر اول: شبکه محلی (MVP)

- میزبان روی Wi-Fi محلی گوش می‌دهد.
- برنامه آدرس LAN و پورت را نمایش می‌دهد و QR شامل همین آدرس می‌سازد.
- اتصال فقط در همان شبکه کار می‌کند.
- فایروال، جداسازی شبکه مهمان و قابلیت AP isolation ممکن است اتصال را مسدود کنند.

### مسیر دوم: اینترنت مستقیم

- IPv6 عمومی در صورت پشتیبانی دو طرف، یا IPv4 عمومی با port forwarding صریح صاحب شبکه.
- آدرس پویا باید با روش امن به‌روز شود؛ DDNS فقط نام را به IP تبدیل می‌کند و به‌تنهایی NAT را دور نمی‌زند.
- UPnP نباید بدون رضایت روشن کاربر پورت باز کند.
- CGNAT اپراتور موبایل معمولاً اتصال ورودی IPv4 را مسدود می‌کند.
- هیچ آدرس ثابت عمومی را نمی‌توان صرفاً با اجرای برنامه روی گوشی تضمین کرد.

### مسیر سوم: معرفی و relay

- سرویس rendezvous فقط شناسه تصادفی میزبان و candidateهای شبکه را با TTL کوتاه نگه می‌دارد.
- تلاش اتصال مستقیم/UDP hole punching فقط وقتی انجام می‌شود که شبکه اجازه دهد.
- اگر اتصال مستقیم ممکن نبود، relay اختیاری بسته‌های end-to-end encrypted را عبور می‌دهد.
- relay نباید داده خام، رمز عبور یا کلید رمزگشایی دریافت کند.
- اگر هیچ مسیر مستقیمی وجود نداشته باشد و relay هم در دسترس نباشد، اتصال از اینترنت ممکن نیست؛ برنامه باید علت را شفاف اعلام کند، نه اینکه وانمود کند سرور آنلاین است.

## الزامات امنیتی غیرقابل مذاکره

1. TLS با گواهی/کلید هویت پایدار و pinning؛ تغییر کلید بدون فرآیند تأیید مجدد نباید بی‌صدا پذیرفته شود.
2. رمزنگاری سرتاسری پیام‌ها و فایل‌ها با پروتکل استاندارد و کتابخانه معتبر (مثلاً پروتکل شناخته‌شده مبتنی بر X25519 و AEAD)، نه طراحی الگوریتم اختصاصی.
3. کلید خصوصی هویت و کلیدهای محلی در Android Keystore؛ هرگز در دعوت‌نامه، log یا backup ناامن قرار نگیرند.
4. در صورت هدف «حتی میزبان هم پیام را نخواند»، رمزنگاری سرتاسری الزامی است. TLS به‌تنهایی کافی نیست؛ سرور فعلی قادر به پردازش داده‌های سمت سرور است و این ویژگی هنوز در وضعیت فعلی تضمین نشده است.
5. توکن‌های دعوت یک‌بارمصرف، کوتاه‌عمر، محدود به میزبان و سطح دسترسی؛ ذخیره hash و مصرف اتمیک برای جلوگیری از race/replay.
6. rate limit، محدودیت اندازه payload، سهمیه فضای دیسک، دفاع در برابر DoS و محدودیت تعداد نشست‌ها؛ سقف اعضا و نشست‌های هم‌زمان باید در backend اتمیک enforce شود.
7. جداسازی کامل داده‌های هر فضای میزبانی و جلوگیری از دسترسی عضو به فایل‌ها، اعلان‌ها، clipboard و داده‌های دیگر گوشی.
8. ثبت رخدادهای امنیتی بدون ثبت محتوای پیام، توکن، رمز عبور یا کلید.
9. توقف فوری پذیرش اتصال هنگام خاموش‌کردن Host و امکان revoke همه اعضا/دعوت‌ها.
10. هیچ HTTP ساده‌ای برای اتصال عمومی؛ HTTP فقط برای loopback یا حالت توسعهٔ محدودشده.

## مدل تهدید و واقعیت امنیت

- خودمیزبانی کنترل داده و وابستگی به سرور مرکزی را کم می‌کند، اما گوشی میزبان را به یک سرویس اینترنتی قابل حمله تبدیل می‌کند.
- میزبان می‌تواند خاموش، بی‌اینترنت، کم‌باتری یا خارج از دسترس باشد.
- اگر پیام‌ها فقط با TLS محافظت شوند، مالک سرور می‌تواند به داده‌های پردازش‌شده سمت سرور دسترسی داشته باشد. برای محرمانگی در برابر میزبان، E2EE لازم است.
- IP میزبان ممکن است برای عضو قابل مشاهده شود؛ relay می‌تواند این افشا را کاهش دهد، ولی هزینه و نقطه اتکای عملیاتی ایجاد می‌کند.
- گوشی گم‌شده/روت‌شده، بدافزار، نسخه دستکاری‌شده و دسترسی فیزیکی از ریسک‌های مستقل هستند.

## محدوده‌بندی پیاده‌سازی

### مرحله 0 — طراحی و اثبات امکان‌پذیری
- تثبیت API فعلی و تهیه قراردادهای HTTP/WebSocket.
- نمونه‌سازی listener محلی Android و آزمون اتصال از دستگاه دوم در Wi-Fi.
- سنجش محدودیت‌های Android 10+، مصرف باتری، Doze و پایداری foreground service.
- انتخاب runtime قابل نگهداری؛ از اجرای بی‌محافظ Python داخل APK یا کپی‌کردن کل backend بدون آزمون اجتناب شود.

### مرحله 1 — میزبان LAN چندسکویی
- اول تثبیت و تکمیل Windows Host موجود: ظرفیت قابل تنظیم، دعوت امن، مدیریت اعضا و تست چندکلاینتی.
- Android در همان مرحله به‌عنوان کلاینت به Windows Host وصل شود و برعکس‌بودن این سناریو برای مرحله بعد آماده گردد.
- سپس Android Host با همان wire protocol و API مشترک ساخته شود؛ فقط پیام‌رسان پایه: ثبت‌نام، ورود، چت خصوصی، گروه، پیام متنی و فایل با سقف محدود.
- ایجاد/توقف میزبان، دعوت QR، تأیید اثر انگشت، revoke عضو و persistence محلی روی هر دو سیستم‌عامل.
- هیچ قابلیت اینترنت عمومی یا relay در این مرحله ادعا نشود.
- آزمون Windows↔Windows، Android→Windows و در زمان تکمیل Android Host، Windows→Android و Android↔Android.

### مرحله 2 — قابلیت‌های کامل پیام‌رسان
- WebSocket، اعلان‌ها، تماس‌ها و رسانه‌ها با سازگاری پروتکل.
- مهاجرت داده و پشتیبان‌گیری رمز‌شده؛ restore باید کلیدهای هویت را با کنترل کاربر حفظ یا به‌صورت امن بچرخاند.
- E2EE برای چت‌های فردی و گروهی، مدیریت تغییر اعضا و key rotation.

### مرحله 3 — اتصال اینترنت
- IPv6/port-forwarding و تشخیص CGNAT.
- rendezvous و relay رمز‌شدهٔ اختیاری.
- تست شبکه‌های موبایل، Wi-Fi عمومی، NATهای مختلف و تغییر IP.

### مرحله 4 — Ghab و Cloud Drive
- فقط پس از ممیزی منابع CPU/RAM/storage و امنیت، این سرویس‌ها به میزبان موبایل منتقل شوند.
- پیش‌فرض محدودیت شدید حجم، سهمیه و نرخ درخواست داشته باشد.
- امکان انتخاب سرویس‌های فعال به‌صورت جداگانه.

## معیارهای پذیرش

- میزبان Windows در حالت LAN بدون سرور خارجی قابل ایجاد و استفاده باشد؛ Android Host نیز پس از پیاده‌سازی runtime مستقل همین معیار را داشته باشد.
- کاربران Android و Windows بتوانند با همان دعوت‌نامه و endpoint به میزبان یکدیگر متصل شوند.
- چند گوشی بتوانند با یک آدرس میزبان متصل شوند و هرکدام حساب و نشست مستقل داشته باشند.
- مالک بتواند سقف اعضای ثبت‌شده و اتصال‌های هم‌زمان را جداگانه تغییر دهد؛ سقف‌ها در برابر درخواست‌های هم‌زمان نیز دور زده نشوند.
- پس از تکمیل ظرفیت، عضو/اتصال جدید با پیام قابل فهم رد شود و نشست‌های موجود بدون اجازه قطع نشوند.
- با حذف یا مسدودسازی یک عضو، دسترسی همان عضو لغو شود و بقیه اعضا تحت تأثیر قرار نگیرند.
- گوشی دوم بتواند فقط با اسکن دعوت‌نامه به میزبان وصل شود.
- اثر انگشت میزبان قبل از ارسال اعتبارنامه قابل مشاهده و تأیید باشد.
- دعوت منقضی/لغوشده/مصرف‌شده و replay شده رد شود.
- عضو نتواند مجوز میزبان یا فایل‌های خصوصی سیستم را به دست آورد.
- پس از توقف میزبان، پورت بسته و اتصال جدید رد شود.
- قطع و وصل شبکه و restart کنترل‌شده باعث خرابی پایگاه داده یا دور زدن مجوزها نشود.
- آزمون‌های خودکار و دستگاه واقعی برای هر مرحله سبز باشند.
- محدودیت دسترسی اینترنتی، NAT، باتری و خاموشی میزبان در UI شفاف نمایش داده شود.

## تصمیم اجرایی پیشنهادی

اول Windows Host موجود را به میزبان چندکاربره با ظرفیت و دعوت امن تبدیل می‌کنیم و سازگاری کلاینت Android با آن را حفظ می‌کنیم؛ هم‌زمان قرارداد مشترک پروتکل را تثبیت می‌کنیم. سپس Android Host را با همان قرارداد پیاده‌سازی می‌کنیم تا Windows و Android هر دو بتوانند هم میزبان و هم عضو باشند. قابلیت اینترنت عمومی، relay و انتقال کامل Ghab/Cloud Drive تا عبور از آزمون‌های واقعی هر دو سیستم‌عامل آماده اعلام نمی‌شود.
